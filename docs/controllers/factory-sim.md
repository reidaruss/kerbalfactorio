## 1. Mission
Deliver Factorio-grade automation depth in 3D — mining, belts, inserters, machines, refining, assembly, power, logistics — at scale, by combining a data-oriented sim, update-on-demand, and the active/on-rails abstraction for distant bases.

## 2. Scope & owned subsystems
- **Data-oriented entity sim** — belts, inserters, miners, smelters, assemblers as tight component arrays, **not** engine Actors.
- **Item transport** — belt segments with compression (items as offsets on a segment, not N objects); inserters; pipes/fluids (later).
- **Recipes & crafting** — data-driven recipe graph; machine processing ticks.
- **Power network** — graph of generators/consumers; per-tick supply/demand; brownout on deficit; solar tied to orbital conditions.
- **On-rails factory abstraction** — a distant/unobserved base collapses to a production-rate model (inputs→outputs over time) instead of per-entity sim.
- **Update-on-demand** — sleeping idle entities; wake on state change.
- **Non-goals:** rendering items/machines (→ rendering consumes our state stream); research/tech tree semantics (→ gameplay; we *produce* science items); save format (→ persistence; we expose state).

## 4. Architecture & approach
- **Sim layout:** components in SoA arrays; systems iterate contiguously. Entities placed on terrain surfaces (world-gen) at grid-snapped or free 3D transforms.
- **Belts:** a belt *segment* stores a flow plus discrete item slots as positions along the segment; only segment heads/tails interact with inserters/machines — avoids per-item objects. Rendering instances item meshes from this state (or a flow texture at distance).
- **Update-on-demand:** entities subscribe to inputs; an inserter with no source/sink sleeps. A dirty/active set drives the per-tick work, not the full entity count.
- **On-rails:** when a base's chunk leaves the active band (core-engine `SimProxy`), snapshot its steady-state throughput and run a cheap rate model; on re-entry, reconstruct buffers from the rate model × elapsed time (bounded by storage). This is also how time-warp advances factories.
- **Power:** each tick, per network: sum generation, sum demand; if demand>supply, scale all consumers by supply/demand (brownout). Solar generation = base × f(sun visibility, distance², atmosphere) from physics/world-gen.

### 5.1 — The POWER surface (FS-20 to FS-25, 2026-07-27). What other lanes need from us.

**What a UI lane needs for the supply-and-demand panel.** Everything is a plain integer read off the last solve; nothing needs a second call into the sim. Via `of::automation::BuildableNetwork`:

```cpp
size_t                     networkCount();                  // how many separate grids exist
NetworkStats               networkStats(NetworkId n);       // BY VALUE (ids re-derive on topology change)
std::vector<NetworkSample> networkHistory(NetworkId n);     // ring buffer, oldest first, for a graph
const std::vector<WireSegment>& wires();                    // exactly N-1 per network
NetworkId                  networkOfBuild(const BuildId&);  // kNoNetwork == no pole reaches it
uint32_t                   satisfactionQ16Of(const BuildId&);
double                     satisfactionOf(const BuildId&);  // the same, as 0..1
```

`NetworkStats { id, capacityW, productionW, demandW, consumptionW, satisfactionQ16, poleCount, generatorCount, consumerCount, fuelledGeneratorCount }` plus `satisfaction()` and `inDeficit()`. **`capacityW` versus `productionW` is the pair that makes the panel worth having**: capacity is what the fuelled generators could make, production is what was actually drawn, and a big gap means "you have spare generators", while `demandW > capacityW` means "you are short". `NetworkSample { tick, productionW, demandW, satisfactionQ16 }`. The single sentence a panel should be able to render is *"120 kW demanded, 90 kW produced, 75%"*, which is the difference between a player seeing "my smelter got slower" and a player knowing to place a generator.

**What a BRIDGE lane needs to export (roadmap blocker D-1).** About fourteen entry points in the `of_net_*` family of `web/wasm/of_core_api.cpp`; nothing in `/core` has to change for any of them. Suggested shapes, matching the existing `of_net_*` conventions (ints in, scratch-array out):

```
of_net_enable_grid(n, on)                                  -> void
of_net_place_pole(n, x, y, z, cls)                         -> poleId
of_net_remove_pole(n, poleId)                              -> 1/0
of_net_place_burner_generator(n, x, y, z, fuelItem)        -> genId
of_net_insert_fuel(n, genId, item, count)                  -> accepted
of_net_generator_fuel(n, genId)                            -> units
of_net_generator_output_w(n, genId)                        -> watts
of_net_connect_to_grid(n, build, x, y, z, ratedDrawW)      -> void
of_net_place_electric_smelter(n, ore, ingot, x,y,z, ticks, powerW, outCap) -> build
of_net_network_count(n)                                    -> count

```

Watts fit an `int32` comfortably at our scale. Energy (`storedEnergyMilliJ`) does NOT fit an `int32` (one coal is 4e9 mJ), so pass it as a double or in joules, not millijoules.

**What a RENDER lane needs (roadmap blocker D-3).** `wireSegments()` gives `WireSegment { a, b, network, ax, ay, az, bx, by, bz }` and there are **exactly (poles in network - 1)** of them, never one per pole pair in reach. A stretched instanced quad per segment is the whole job.

**What needs ART: nothing.** The electric smelter, the burner generator and the power pole reuse shipped TypeIds **0x12**, **0x15** and **0x16** (ASSET-SPECS §4.15 / §4.18 / §4.19; `machines/smelter.glb`, `machines/generator.glb`, `machines/power_pole.glb` are all built). ### 5.3 — ITEM ACCEPTANCE (FS-37, 2026-07-27). What a placement or UI lane may rely on.

```cpp
bool   FactorySim::machineAcceptsItem(EntityHandle machine, ItemId item) const;
ItemId FactorySim::inserterHeldItem(EntityHandle inserter) const;
```

Both additive, both pure reads, no signature changed. `machineAcceptsItem` is the **single** definition of "will this machine take this item": true iff the item is the machine's current recipe's slot-1 or slot-2 ingredient. **A wiring layer that wants to avoid building a doomed inserter should ASK it rather than re-deriving the rule** — a second copy of this predicate in `FactoryWiring.ts` would be the duplicate-authority mistake one balance pass away from disagreeing with the sim. A ghost/prompt lane can use the same call to grey out or explain a connection before it is made. `inserterHeldItem` exists so an identity ledger can see the one unit legitimately in transit; anything auditing conservation per item type needs it or it is off by one, by tick phase.

Behaviour a caller can count on: a refused item is **never destroyed**. It stays on its belt (or in the source's out-slot) and the line backs up exactly as it does behind a full machine, so "my belt is jammed" is the visible symptom of a mis-typed connection, which is what Factorio does too.

## 7. Open questions & risks
- **R8 (new, 2026-07-27, FS-40b): every driven client probe in this lane runs on the SPAWN CLEARING, which is FLAT, and a whole class of belt and machine geometry defect is identically zero there.** FS-40 is the proof: 39 real R presses, three hand-built topologies and a 36-press storm all measured 1e-6 m on the clearing while the same gestures on a 14.82 degree hillside measured 0.101 m. `beltslope.js` is the first probe in this lane to teleport to measured sloping ground, and it should not be the last: `beltsnap`, `beltcargo`, `autoline` and `demolish` all make geometric claims that have only ever been checked where the ground is level. Cheap to fix (the teleport-and-measure sweep is about 25 lines) and worth doing before the next "it looks wrong in my world" report.
- **R9 (new, 2026-07-27, FS-41): `x || fallback` is used as a default across this client, and this codebase uses 0 as `kNoItem` and -1 and 0 as sentinels elsewhere.** The coal-to-iron smelter was one instance; a grep for `|| ids.` and `|| kNo` found four, all in the same expression. The general repair is not a lint rule but a habit: a fallback that replaces one half of a pair is a fallback that can invent a combination neither half ever meant. Named here because the next instance will not look like this one.
- **R5 (the browser render wall, DW-27's question 3): CLOSED for the pool, OPEN as a triangle budget (FS-16, 2026-07-26).** The integrated real-hardware case R1 left open has now been measured in the shipping client, and what bound it was neither `pathUnitToWorld` nor LOD hysteresis: it was a fixed-size JS array. With the pool growing, **draw calls do not move with factory size at all** (45 for the whole factory from 60 to 900 machines, 49 with a base, against a budget of 150) and frame time barely does (p50 1.8 to 2.0 ms). **The binding constraint is TRIANGLES**: 2,111,874 at 900 plan rows against a 2.7 M alert, a slope of 2,119 per row, so alert at about 1,180 machines and fail at about 2,080. **A second, unexpected finding:** more than half the instances on screen at 900 rows are DW-9 inserters, because `FactoryWiring.touch` gives belt-to-smelter 2.25 m of reach and a dense parallel layout puts lanes 2.2 m apart, so every smelter wires into its neighbouring lanes. Those connections are real, but it means the triangle cost of a big base is dominated by auto-created inserters rather than by the machines a player placed. Reported, not fixed. Still not measured: `/core`'s per-tick cost at that scale, because the seeded belts carry no ore (a drill needs an ore patch under it, DW-25, and there is not enough patch to feed hundreds).
- **R1 (the render wall) — render half NOW NUMERICALLY BACKED HEADLESSLY (FS-14, gate G7); integrated real-hardware case still Phase-1.** Sim scale ≠ render scale (Spike 3 §7.4). Spike 3 retired the *sim* half (100k entities + millions of items @ 60 UPS) and pinned the §6 stream; **FS-14 now EMITS that stream and proves, with a numeric render-cost model (`render_cost.h`), that the §6 contract clears the wall: a 100k-entity stress scene → 72 draw calls (not 100k), 180k item-evals vs 12.18M belt items (>98% collapsed) — the O(items)→O(lines) collapse + draw-calls-track-type-variety, quantified.** This is RC-8 (rendering's "confirmed on paper") validated without a GUI. Still open (the bit a cost model *can't* measure): the **integrated 100k-*rendered*** case on real hardware — LOD-0 `pathUnitToWorld` instance-build cost (rendering R5), Nanite-on-small-meshes, LOD-band hysteresis — a **Phase-1 co-validation with rendering**, owned jointly.
- **R2 (on-rails dupes/accuracy) — RETIRED for the synthetic-recipe case (FS-12, gate G2 PASSED).** Built + tested: buffer-cap bound + deterministic `TickIndex` reconstruction + exact integer-craft replay ⇒ **zero dupes** (on-rails produced == continuous-active produced, never greater) and a hard storage ceiling even under a 1.89 B-tick warp. Residual (unchanged): rate-model accuracy for deep multi-stage recipes (naive bottleneck ≠ true steady-state) — Phase-2 refinement, harmless for the single-stage synthetic recipes the gate uses.
- **R6 (new, 2026-07-27): the power model has never been driven in the client, and the panel is where it becomes a feature.** `/core` proves the arithmetic, the topology and the determinism with 1,330 checks, but nobody has yet placed a pole in the game, watched a network split when they demolished one, or seen a satisfaction number move. Two of the three handoffs (the bridge exports, the panel) are the difference between a correct model and a played one. The residual risk is not correctness, it is ERGONOMICS: 2.5 m of supply radius on a 1.002 m site grid is a number chosen against Factorio's proportions and our own reach constants, not against a player's hands. Expect to retune it once somebody plays it, which is cheap because it is one row of `poleClassDef`.
- **R7 (new, 2026-07-27): the grid re-partitions in O(P^2) in the number of poles, and only when the topology changes.** `rebuild()` is an all-pairs pole scan plus an all-pairs node-to-pole scan, run lazily on a dirty flag, so the per-tick cost is zero and the placement cost is quadratic. At a few hundred poles that is microseconds and invisible. It is written down because the shape of the failure is familiar: it is fine until a base gets big, and then it is a hitch on every pole placement rather than a steady cost. A uniform-grid spatial hash over pole positions makes it near-linear whenever that day arrives; there is no reason to build it now and every reason to have named it.
- **R3:** 3D placement ergonomics vs Factorio's 2D grid clarity (overlaps with gameplay UI). *(unchanged)*
- **R4 (new, from Spike 3 §9):** **Mass Entity binding overhead** — the *algorithm* passes headless (G1); whether UE Mass Entity's processor/fragment dispatch regresses 100k below 60 UPS is a D-001 stress point (G8). Isolated by headless-first plan; if it fails, fix is a thinner SoA path under UE, not a re-scope. The real limiting factor at 100k is **memory bandwidth / cache misses, not arithmetic** (boids reference: 100k in ~2.4 ms tight-SoA).

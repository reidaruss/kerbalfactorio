## 1. Mission
Deliver Factorio-grade automation depth in 3D — mining, belts, inserters, machines, refining, assembly, power, logistics — at scale, by combining a data-oriented sim, update-on-demand, and the active/on-rails abstraction for distant bases.

## 2. Scope & owned subsystems
- **Data-oriented entity sim** — belts, inserters, miners, smelters, assemblers as tight component arrays, **not** engine Actors.
- **Item transport** — belt segments with compression (items as offsets on a segment, not N objects); inserters; pipes/fluids (later).
- **Recipes & crafting** — data-driven recipe graph; machine processing ticks.
- **Power network** — graph of generators/consumers; per-tick supply/demand; brownout on deficit; solar tied to orbital conditions.
- **On-rails factory abstraction** — a distant/unobserved base collapses to a production-rate model (inputs→outputs over time) instead of per-entity sim.
- **Update-on-demand** — sleeping idle entities; wake on state change.
- **Non-goals:** rendering items/machines (→ rendering consumes our state stream); research/tech tree semantics (→ gameplay; we *produce* science items); save format (→ persistence; we expose state).

## 4. Architecture & approach
- **Sim layout:** components in SoA arrays; systems iterate contiguously. Entities placed on terrain surfaces (world-gen) at grid-snapped or free 3D transforms.
- **Belts:** a belt *segment* stores a flow plus discrete item slots as positions along the segment; only segment heads/tails interact with inserters/machines — avoids per-item objects. Rendering instances item meshes from this state (or a flow texture at distance).
- **Update-on-demand:** entities subscribe to inputs; an inserter with no source/sink sleeps. A dirty/active set drives the per-tick work, not the full entity count.
- **On-rails:** when a base's chunk leaves the active band (core-engine `SimProxy`), snapshot its steady-state throughput and run a cheap rate model; on re-entry, reconstruct buffers from the rate model × elapsed time (bounded by storage). This is also how time-warp advances factories.
- **Power:** each tick, per network: sum generation, sum demand; if demand>supply, scale all consumers by supply/demand (brownout). Solar generation = base × f(sun visibility, distance², atmosphere) from physics/world-gen.

## 5. Interfaces & dependencies
**Depends on (inbound) — we *consume* these, pinned by core-engine Spike 1 §5 (no changes requested):**
- core-engine: `ISimClock` (`FixedDt`, `Alpha()`, `TickIndex()`, `OnFixedTick`), `ISimProxy`/`ISimRegistry` (active/on-rails promote/demote + bubble/hysteresis — we implement the content hooks, §FS-7). **`ISimProxy` now carries a defaulted `PromotionRadius()` accessor (core-engine RC-10, spike1-core-engine §5.3); our `FFactoryChunkProxy` OVERRIDES it (FS-9/CE-7) to return the chunk bounding-sphere half-extent so the extent-aware bubble test (§3.2.1) uses the chunk's near edge — `Position()`/`Velocity()` unchanged.** `UniverseCoord`/`FFrameId`/frames for placement.
- world-gen: deposit catalog (for miners), build-surface/collision (for placement). **Solar `AtmoTransmittance`** (from `FAtmosphereProfile`) for power.
- physics: **solar `SunVisibility` + `DistanceToStarM`** (from `FReferenceFrame::ToUniverse`/SOI geometry) for power. *(Spike 3 defines `ISolarProvider::SampleSolar` and stubs it; physics+world-gen implement in Phase 1 — see DEPENDENCY below.)*

**Provides to (outbound) — published contracts (PINNED in Spike 3 §6; rendering+networking to confirm):**
- **Entity-state stream** → [rendering](rendering.md) — *lossy/interpolated, delta-only, drained at render FPS.* Two records:
  - `FFactoryEntityState { FEntityId Id; uint16 TypeId; FUniverseCoord Position; FQuat16 Orientation; uint8 VisualState, AnimPhase, Lod, Flags; uint16 BoundRadius; }` (**~34 B**, instancing-friendly). **`BoundRadius` (FS-9/RC-12, append-only +2 B)**: packed bound-radius (cm) about `Position`, sourced from `StaticDef.AABB` (§1.3) — lets rendering frustum-cull + pick LOD band by screen-size with no per-`TypeId` asset-bounds lookup. Same bounds data backs the `PromotionRadius()` override above.
  - `FFactoryBeltFlowState { FEntityId LineId; uint16 ItemTypeDominant; uint8 FlowSpeedQuant, Density, Compressed; }` + on-demand `GetLineItems(LineId)→{itemType,unitOffset}[]`.
  - **Render-wall contract:** `GetLineItems` (the only O(items) call) is pulled **only at RN-3 LOD-0**; at LOD-1+ belts are a scrolling-flow material (`FlowSpeedQuant`/`Density`) → render item cost collapses to O(lines). This is how sim-scale (millions of items) decouples from render-scale.
- **Delta/event stream** → [networking](networking.md) — *lossless/ordered, keyed by `TickIndex()`.* `FFactoryDelta { uint64 TickIndex; EFactoryEvent Type; FEntityId Entity; uint32 A,B; }`; `EFactoryEvent ∈ {EntityPlaced/Removed, RecipeChanged, InventoryChanged, BeltStateChanged, InserterTransfer, MachineCompleted, PowerStateChanged, ProxyDemoted/Promoted}`. Chunk-local determinism lets networking client-sim a chunk and correct only on divergence (NW-4).
- **Factory state snapshot** (entities, buffers, power, on-rails `FRailState` rate models) → [persistence](persistence.md). **C-6 (FS-10): we implement persistence's `IPersistable` chunk-scoped (`DomainId=FactorySim`) = per-entity SoA when the chunk is active / `FRailState` when on-rails (spike3 §11.3); reuses the §5 demote/promote machinery, inherits G2 no-dupe, adds no persistence dupe surface.**
- **Recipe + entity schema** (`FRecipeDef` / `FEntityDef`) → [gameplay](gameplay.md) authors content. **C-2 (FS-10): we DEFINE + EXECUTE the schema (recipe drives `MachineProc`/`Inventory`; entity def = machine-type id, recipe slots, power, footprint/AABB, IO port layout); gameplay AUTHORS the values + appends UX/cost fields the sim ignores. `ItemId` is gameplay's opaque C-3 handle — we treat it as an uninterpreted `uint16` key. Pinned: spike3 §11.1.**
- **Player intent → sim mutation** (`IFactoryBuildIntent`/`IPlaceBeltIntent`/`IRemoveEntityIntent`/`ISetRecipeIntent`/`ITransferItemsIntent` + `QueryEntityInventory` read) from [gameplay](gameplay.md). **C-5 (FS-10): CONFIRMED — every intent is a command (not a state write, D-004-clean); the sim validates + applies it as a server-authoritative mutation at the next fixed-tick boundary, emitting the matching `FFactoryDelta`; no intent mutates SoA directly; `QueryEntityInventory` is a pure read of committed state. Intent→mutation map: spike3 §11.2.**
- **Production outputs** incl. science packs & item availability (via `MachineCompleted`) → [gameplay](gameplay.md).
- **Factory chunk spatial extent (C-8, FS-10):** a factory chunk = **~1 km × 1 km** surface footprint (bounding-sphere half-extent ≈ 0.7 km = our §5.4 `PromotionRadius()`). Fits inside the 2 km activate band as a promote/demote unit (FS-7); lands a slice factory in one chunk. **Routed to core-engine + persistence: core-engine sets `FChunkKey.RegionDepth` per body so 1 region quad ≥ our ~1 km extent; for E ≈ 1 km it LOCKED Forge depth 9 / Cinder depth 8 (per PHASE1-PLAN §10, 2026-06-14; this REPORT had earlier estimated ≈10 for Forge — core-engine's "smallest depth ≥ E" rule lands one shallower at 9). We ALIGN our chunk granule (`ISimProxy`/`FChunkKey` unit) to that depth → 1 save region == 1 factory chunk proxy.** Stated: spike3 §11.4.
- **Solar interface (DEFINED here, IMPLEMENTED by physics/world-gen later):** `ISolarProvider::SampleSolar(panelPos, SimTime)→FSolarConditions{SunVisibility, DistanceToStarM, AtmoTransmittance}` (Spike 3 §4.4).

**Determinism note:** factory chunks are *locally* deterministic given their inputs (integer/fixed-point hot path; fixed system + shard order) even though the whole game isn't lockstep — enables networking's client-side factory simulation (NW-4). The one float (power brownout ratio) is applied as a fixed-point per-network scalar in fixed order.
**FLAGGED:** §6 stream contracts were "negotiate later" per rendering/networking — Spike 3 pins them; **rendering confirms `FFactoryEntityState`/`FFactoryBeltFlowState` + LOD-0-only `GetLineItems` satisfies RN-3; networking confirms `FFactoryDelta` keyed by `TickIndex()` is a sufficient replication seam.** We *consume* core-engine's `ISimProxy`/`PromotionRadius()` — no core-engine contract changed.

## 7. Open questions & risks
- **R1 (the render wall) — NOT retired by Spike 3, by design; owned jointly with rendering.** Sim scale ≠ render scale (Spike 3 §7.4). Spike 3 retires the *sim* half (100k entities + millions of items @ 60 UPS) and pins the §6 stream whose **LOD-0-only `GetLineItems`** rule lets rendering's RN-3 ladder collapse per-item cost to O(visible lines) past LOD-0. The integrated **100k-*rendered*** case is a **Phase-1 co-validation with rendering** — the single biggest cross-risk, explicitly left open.
- **R2 (on-rails dupes/accuracy) — addressed (Spike 3 §5.3), gated by G2.** Buffer-cap bound + deterministic `TickIndex` reconstruction + conservative under-fill ⇒ no dupes/exploits. Residual: rate-model accuracy for deep multi-stage recipes (naive bottleneck ≠ true steady-state) — Phase-2 refinement, harmless for synthetic recipes.
- **R3:** 3D placement ergonomics vs Factorio's 2D grid clarity (overlaps with gameplay UI). *(unchanged)*
- **R4 (new, from Spike 3 §9):** **Mass Entity binding overhead** — the *algorithm* passes headless (G1); whether UE Mass Entity's processor/fragment dispatch regresses 100k below 60 UPS is a D-001 stress point (G8). Isolated by headless-first plan; if it fails, fix is a thinner SoA path under UE, not a re-scope. The real limiting factor at 100k is **memory bandwidth / cache misses, not arithmetic** (boids reference: 100k in ~2.4 ms tight-SoA).

## 1. Mission
Make the project buildable, testable, and reproducible. Own version control, the toolchain, the headless test harness that the entire "prove it Wave-0 first" thesis depends on, CI, and the asset pipeline. If a domain can't build or test its core, that's this controller's problem.

## 2. Scope & owned subsystems
- **Version control** — git repo, `.gitignore` (UE5 + build artifacts), branch/commit conventions, Git LFS for binary assets.
- **Toolchain** — UE5 version pinning, Visual Studio 2022 / MSVC, project generation, dependency management.
- **Headless test harness** — the standalone C++ test project (no UE5 dependency) + framework (Catch2/GoogleTest) for the Wave-0 pure-CPU cores; the bench harness for the 100k @ 60 UPS claim.
- **CI** — automated headless tests per commit; later, UE5 build CI.
- **Asset pipeline** — placeholder-art workflow for the slice; LFS + import conventions; cooking/packaging later.
- **Non-goals:** the gameplay/sim code itself (each domain owns its code + its tests); art *content* (Reid's hiring/asset call); the design (the controllers).

## 4. Architecture & approach
- **Two build targets:** (1) the **headless core lib + tests** — pure C++, CMake or minimal MSVC solution, no UE; each domain's Wave-0 core compiles here and is unit/bench-tested. (2) the **UE5 project** — created after the headless cores pass, links the core libs.
- **Gates → tests:** translate the spike gate lists (V/WV/RV/G-series) into automated tests; headless gates run in CI, in-engine gates run manually post-M2.1 (EXECUTION-PLAN §4).
- **Repo layout (proposed):** `/docs` (design), `/core` (headless libs + tests), `/ue` (the UE5 project), `/tools` (scripts/CI). Single repo, LFS for `/ue` binaries.

## 5. Interfaces & dependencies
**Depends on (inbound):** Reid's go-ahead to init git + install the toolchain; each domain's Wave-0 core source (they write it, this harness builds/tests it).
**Provides to (outbound):** a working build + test + CI environment for every domain; the headless harness API (how a domain registers its core's tests/benches); the repo + LFS.
**Cross-cutting:** like networking, this touches every domain — but as *infrastructure they build on*, not sim they depend on.

## 7. Open questions & risks
- **R1:** does the user's machine have the VS2022/MSVC + UE5 toolchain installed? (Verify before the build greenlight.)
- **R2:** sharing C++ code between a headless lib and a UE module cleanly (UE's build system vs plain CMake) — keep cores as engine-agnostic libs.
- **R3:** Nextcloud + git in the same folder can fight (sync vs `.git`); confirm the repo location/ignore rules.
- **R5 (opened 2026-07-26, BT-10) and it is not this domain's to fix:** the factory render batch is a fixed 256 instances (`web/src/game/MachineBatch.ts:26`), reached at about **150 machines**, and exceeding it is **silent**: the machines simulate, produce and persist, and are never drawn, with draw calls, triangles, frame time and every budget indicator unchanged. Escalated to Admin for the **rendering** domain (give the batch a growth path) and for **gameplay/UI** (an instance-pool exhaustion line in the HUD budget, next to draw calls). Until it is fixed, no performance claim about a large factory means anything, including the reassuring ones in this spike. Re-running `electron/probes/scale.js` unchanged is the acceptance.
- **R6 (opened 2026-07-26, BT-11) and it is not this domain's to fix: the 4 m rescale needs a CLIENT pass, and one number in it is load-bearing.** `StructureGrid.measureModule` reads the module off the shipped sockets, so most of `web/src/game` follows for free. These do not, in order of consequence.
  1. **`Structures.ts:77` `FLOAT_TOLERANCE_M = 0.55` must be RE-MEASURED, not scaled.** It was set against a **1 m** footprint whose worst measured corner spread on a slope was 0.118 and 0.127 m, comfortably inside a bound whose real driver was the levelling tool's half-voxel dead band. The same slope across a **4 m** footprint spreads roughly four times as far, so the terrain term alone now consumes the whole allowance and an ordinary slope becomes unbuildable, which closes off DW-24's own teaching loop. Re-run `probes/buildtol.js` with the 4 m footprint and re-derive. **This is the one that will look like "foundations stopped working" if it is missed.**
  2. **`Structures.ts:110` module fallback** `{ cellM: 1, deckH: 0.5, wallH: 2.5, wallT: 0.25, storey: 3 }` -> `{ cellM: 4, deckH: 0.5, wallH: 3.5, wallT: 0.25, storey: 4 }`. This is the ONE place a stale 1 m module can survive silently, because everything else measures.
  3. **`StructureGrid.ts:43` `SITE_REACH_M = 32`** is now only 8 cells across a site where it was 32. Suggest 64 (16 cells); tangent-plane departure from a 600 km sphere at 64 m is 3.4 mm, still far below anything visible. **Shared with `MachinePlacement.ts`**, where BT-10 measured it bounding one adopted site at 323 machines, so raising it moves the factory scale test too.
  4. **`StructurePlacement.ts:30` `REACH_M = 12.0`** is three cells at 4 m: you cannot reach the far edge of the cell you are aiming at from inside a room. Suggest 20 to 24, and `FALLBACK_M 3.0` -> 6.0.
  5. Comments that are now wrong: `StructureGrid.ts:45` (`MAX_LEVEL = 3`, "Four is 12 m" is now 16 m; the value can stand), `StructureGrid.ts:10-11` (cites a 1.00 m mesh and a 0.41 m lattice gap; the argument gets STRONGER at 4 m, the numbers are stale), `Structures.ts:52` (quotes the 1 m `buildtol` figures).
  6. Unchanged and worth confirming rather than editing: `BURY_TOLERANCE_FALLBACK_M = 0.50` still equals `DECK_H`, and `swingSecs 0.4167` still matches the shipped clip.
  7. **New, does not exist yet:** nothing in the client places a pillar or knows what an unsupported overhang is. `pillar.glb` should be measured the way `measureModule` measures the module (`PillarFoot/socket_top`, `PillarHead/socket_deck`), never retyped. Whether a pillar is a `StructureKind` at all is a placement-lane design call, since it is auto-generated under an overhang rather than player-placed.
  8. **Costs live in `/core`** (`survival::StructureKind` via `_of_gp_structure_info`), so they are a gameplay call: one foundation now covers **sixteen times** the ground it did, and an unchanged price divides the cost of a base by 16. `Demolition.ts` refunds follow.
- **R7 (opened 2026-07-27, BT-20) and it is not this domain's to fix: armour has NO referent in `/core` at all.** `grep -riE 'armor|armour|equip' core/include` returns nothing, and `web/src` has no equipment concept either: `slot` there means an inventory slot, a hotbar slot or a batch instance index. The meshes ship and validate and nothing can wear one. The concrete shape gameplay needs: `enum class EquipSlot : uint8_t { Head, Chest, Legs, Feet, Count }` with the four values matching the four node names exactly, so the client's lookup is an array index and never a string built at runtime; `ItemCategory::Armour` added to the existing enum; `ItemDef` gaining `EquipSlot slot` plus a stat block for armour rows with `stackMax = 1`; a `std::array<ItemStack, EquipSlot::Count>` on the player with `equip`/`unequip` returning the displaced stack; four new `ItemId`s in the pinned append-only block; and a `setId` so the renderer knows which `.glb` to load. Serialisation is 4 slots x 4 B = 16 B, which the save schema needs a version bump for. Escalated to Admin for **gameplay** and **persistence**. Separately and smaller: **an armoured player still sees unarmoured first-person arms**, because `armour_set` carries the third-person 44-bone rig and the view model is a different 27-bone rig with a different bind pose. Either a second armour file against `FP_BONES` or a decision to accept it.
- **R4 (opened 2026-07-26, BT-9):** the four structural parts are the first Tier-0 assets with **no referent in the headless headers**. `automation.h`'s `BuildKind` has no `Foundation`/`Wall`/`Floor`/`Door`, `gameplay.h` has no structural items, and there are no `TypeId`s. The meshes ship and validate, but nothing can place one until **factory-sim** adds the `BuildKind` values and `TypeId`s and **gameplay** adds item ids and recipes. Also unanswered and not an art call: does a foundation deform terrain (world-gen/physics voxel interaction) or merely rest on it? Art has published geometry and anchors only. Escalated to Admin.

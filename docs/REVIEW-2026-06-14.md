# Independent Technical Review — Orbital Foundry design doc set

> **Reviewer:** Independent technical / red-team auditor (no stake in the design) · **Date:** 2026-06-14
> **Scope:** the whole planning corpus — `CLAUDE.md`, `MASTER_PLAN.md`, `AGENT_ARCHITECTURE.md`, `controllers/ADMIN.md`, the 3 Phase-0 spike groups (Spike 1 core-engine/world-gen/rendering, Spike 2 physics, Spike 3 factory-sim), the Phase-1 docs (`PHASE1-PLAN`, `gameplay-phase1`, `persistence-phase1`), and all 8 controller files.
> **Verdict in one line:** The design work is genuinely strong — unusually so for a planning-only repo — but **"build-ready" overstates it**: there is a real, unresolved cross-doc contradiction on a pinned contract (C-8 `RegionDepth`), a stale dropped field still threaded through the gameplay docs (`DepositTypeId`), and an entire class of project-execution concerns (toolchain/CI, testing strategy, audio, art pipeline, schedule/team) with **no owner anywhere**. None of it is fatal; all of it should be fixed or consciously deferred *before* anyone calls the plan executable.
>
> **Severity legend:** **BLOCKER** (must fix before build / invalidates a "closed" claim) · **SHOULD-FIX** (real defect, fix soon) · **MINOR** (small/cosmetic) · **NOTE** (observation, no action demanded).

## 1. Requirements coverage

Mapping the original ask → where it lives. Overall coverage is high; the gaps are mostly *honestly deferred*, with two exceptions that have **no clear home**.

| Requirement | Addressed where | Status |

| KSP-grade physics | Spike 2 (patched conics + hybrid integrator), D-002 | **Covered (designed, unbuilt)** |

| Mining / auto-mining / refining / assembly | Spike 3 factory-sim, gameplay-phase1 §2–3, §7 recipe set | **Covered for the slice** (auto-mining = a placed miner; deeper automation deferred) |
| Power management | factory-sim §4 (graph + brownout), HUD beat in gameplay §5.1 | **Covered** |
| Structures + loot + exploration incentive | Off-world resource identity (WG-4 / Cinderite) is the only piece in the slice; **loot/POIs/structures deferred to Phase 4** (gameplay §2, PHASE1-PLAN §3) | **Partially deferred — has a home (gameplay, Phase 4)** |
| Questline | gameplay GP-4/GP-11 (scripted spine in slice; quest engine Phase 4) | **Deferred — has a home** |

| Multiplayer | networking controller (constraint from day one, impl Phase 3), D-004 | **Deferred — has a home, but see §3/§4** |

**Findings:**

- **[NOTE]** Every headline gameplay pillar that's cut from v1 (research, voxel dig, loot/POIs, MP, time-warp, 1M-scale) has an explicit owner and phase. That is good scope discipline (MASTER_PLAN §9, PHASE1-PLAN §3).
- **[SHOULD-FIX] "Auto-mining" is quietly thinner than the ask implies.** The user asked for "mining/auto-mining." In the slice, a miner is a placed machine on a node (gameplay §2.2) — that is automated extraction, fine. But there is **no design anywhere** for the next obvious step (mining drones / automated prospecting / belt-fed auto-deposit-hopping). It's not wrong to defer, but it isn't *named* as deferred the way research/loot are — it's simply absent. Add a one-line "auto-mining beyond placed miners → Phase 2+" so it has a home.
- **[NOTE] Perspective (1st vs 3rd person)** was an implicit requirement-shaper and is resolved sensibly (P1-D1 / GP-6), pending Reid's confirm.

## 2. Cross-doc consistency

This is where the audit found the **most serious problems.** The contract *shapes* are impressively consistent (FUniverseCoord+FFrameId threading, ItemId width, FEntitynDef superset/subset, body constants) — but two pinned numeric/field facts are **out of sync across docs**, and one of them is the very contract the brief flagged.

### 2.1 C-8 `RegionDepth` — a genuine THREE-WAY contradiction, and the "LOCKED" value is propagated nowhere

This is the headline consistency defect. There are **three different `RegionDepth` claims live in the repo simultaneously**, and the doc-debt note that's supposed to cover it does not actually reconcile them.

| Source | Claimed value | Stated chunk extent E | Self-consistent? |
|---|---|---|---|
| **PHASE1-PLAN §10 (C-8 row, marked "LOCKED — Admin reconcile")** | Forge **9** / Cinder **8** | "~1 km" | Yes — `floor(log2(R·π/2 / 1000))` = Forge 9, Cinder 8 ✓ |
| **core-engine CE-9 / spike1-core-engine §5.5, §8** | Forge **11** / Cinder **9** | "assumed 256 m" | **No** — `floor(log2(R·π/2 / 256))` = Forge 11, Cinder **10**, not 9 |
| **factory-sim spike §11.4** | "**≈ depth 10**" on a 600 km body | "~1 km" stated extent | Internally ≈ but says 10, not 9 |
| **persistence-phase1 §3.1 + persistence.md** | "**depth 5–6**" (placeholder example) | "a few km" | Stale placeholder, never updated |

I verified the formula numerically:

- E = 256 m → Forge **11**, Cinder **10**
- E = 1000 m → Forge **9**, Cinder **8**

**Conclusions:**

- **[BLOCKER] The locked value (Forge 9 / Cinder 8) is correct for the 1 km extent factory-sim actually stated — but it is recorded in exactly ONE doc (PHASE1-PLAN §10). Every other doc that mentions `RegionDepth` still carries a wrong/stale number:** core-engine's controller header, CE-9 decision, §5 interface, backlog, and R4 all say **11/9**; the core-engine spike §5.5/§8 says **11/9** under a 256 m assumption; factory-sim §11.4 says **≈10**; persistence still says **5–6**. A reader who opens the core-engine controller (the authoritative domain owner for this value) gets the wrong number. This is precisely the kind of divergence D-006 was created to prevent, reproduced for a different constant.
- **[SHOULD-FIX] The PHASE1-PLAN "doc-debt to fix at build" note is itself stale/incomplete.** §10 says "core-engine CE-9 (11/9 → 9/8) and persistence §3.1 (5–6 → 9/8) should reflect the locked values." It (a) names only 2 of the ~6 stale locations (misses factory-sim §11.4's "≈10", core-engine's controller header, §5, backlog, R4), and (b) the *Cinder* placeholder it's "correcting from" (9) was itself arithmetically wrong even on the 256 m assumption (should have been 10). So the reconciliation paper-trail is muddled: the right answer exists, but the chain of how it was derived contains at least one arithmetic error and the fix-list is under-scoped.
- **[NOTE]** This is the single clearest counter-example to the ADMIN/PHASE1 claim that the contract surface is "ALL CLOSED." C-8 is *decided* but **not propagated**, which is not the same as closed. A contract is only closed when every consumer reads the same number.

### 2.2 `DepositTypeId` — a dropped field still threaded through the gameplay docs

- **[SHOULD-FIX]** WG-11 (and PHASE1-PLAN §10 C-1) explicitly **collapsed `DepositTypeId` into the shared `ItemId`** — "the proposed `DepositTypeId` indirection dropped; the `Resource` field IS the gameplay `ItemId` directly." World-gen's docs are clean. But the **gameplay docs were never updated**: `gameplay-phase1.md` still uses `DepositTypeId` in §2.2 (mining interaction), §3.4 (the commit intent), §7.2 (recipe table prose), the §8.A struct (`uint16 DepositTypeId`), and §8.C (`world-gen ... stores DepositTypeId and the registry maps it to ItemId`). Both gameplay controller refs (gameplay.md §5, gameplay-phase1 §8.A/§8.E) still describe a `DepositTypeId→ItemId` map that **no longer exists** in the pinned C-1. The `IFactoryBuildIntent` carries `FDepositId Deposit` (correct), but the surrounding prose still says the miner "tags placement with the `DepositTypeId`." This is a live shape contradiction between two domains on a *closed* contract — a builder reading gameplay would implement an indirection world-gen deliberately removed.

### 2.3 Items that ARE consistent (verified — credit where due)

- **[NOTE] `ItemId`** is `uint16`, opaque, hand-assigned, single id-space — consistent across gameplay (C-3/GP-13), factory-sim (§1.3, §11.1 treats it as opaque key), world-gen (`FDepositNode.Resource`), and persistence (serializes the raw u16). Clean. (Only the `DepositTypeId` residue above mars it.)
- **[NOTE] `FEntityDef` superset/subset** is correctly and explicitly handled: factory-sim §11.1 defines the *executable* schema; gameplay §8.B authors a *superset* adding `BuildCost`/`SlopeToleranceRad` that "the sim ignores"; both share `TypeId`/`Ports`/footprint. factory-sim even routes a REPORT line asking gameplay to confirm the superset relationship. Good.
- **[NOTE] Body constants (D-006)** are consistently consumed-not-hardcoded across world-gen (`FBodyParams`), rendering (`SCALED_K = 1/RadiusM`, asserts nothing hardcoded), and physics (μ from `FReferenceFrame`). World-gen §5 even flags that it *proposed* the numeric values and Admin must confirm core-engine adopts them — the one open item (WR3/R4) is correctly surfaced, not silently assumed. The single residual: core-engine's spike pins only the *shape* of the rails (`{radius,period,phase}`) and never the numeric μ/SOI, so the actual numbers live only in world-gen §5.1/§5.2. **[MINOR]** worth Admin explicitly logging the agreed constants into D-006 or MASTER_PLAN §11 so there is one canonical table, not "world-gen proposed, core-engine presumed."
- **[NOTE] `FUniverseCoord`+`FFrameId` threading** is consistent and well-policed — every domain's contract restates "a coord carries its frame, never a bare FVector," and world-gen/physics/rendering all echo it. This is the strongest-threaded invariant in the set.
- **[NOTE] `SurfaceHardness` type** was reconciled cleanly: physics first sketched `uint8 0..255` (spike2 §5.2), world-gen published `[0,1] double` (WG-10/RC-7); both docs now acknowledge the tightening. Good closure.

## 3. Risk honesty / over-optimism

The docs are, to their credit, **mostly honest** about the designed-vs-built gap — there is repeated, explicit "designed on paper, not built" language. But the *aggregate framing* (status dashboards, "build-ready," "ALL CLOSED") reads more finished than the substance supports, and a few specific claims outrun their evidence.

**Where the honesty is genuinely good (credit):**

- **[NOTE]** PHASE0-SUMMARY §2 and §5 are admirably blunt: "No engine-overturning blocker was found *on paper*"; "Still must be proven by building"; "the render wall... is the highest remaining unknown." M1 in ADMIN §7 explicitly says "the actual 'pass' needs the Wave-0 headless cores + UE gates."
- **[NOTE]** The Chaos hybrid (PH-4) is handled with real intellectual honesty — it's framed not as "Chaos works" but as "we removed flight integration from Chaos so the riskiest dependency only has to do its happy-path job," with a fallback ladder to fully-custom contact. That's good risk engineering.
- **[NOTE]** Factory-sim §7.4/§9 repeatedly and explicitly says "sim scale ≠ render scale," names the limiting factor (memory bandwidth, not FLOPs), and refuses to claim the render wall is retired.

**Where confidence outruns evidence:**

- **[SHOULD-FIX] "Build-ready" / "Phase-1 planning COMPLETE" is overstated given §2.1–2.2.** ADMIN §2 and PHASE1-PLAN §11 both assert the plan is build-ready and the contract surface "ALL CLOSED." But C-8 is contradictory across 4+ docs and C-1's `DepositTypeId` is stale in gameplay. You cannot hand these briefs to a builder and get a consistent implementation. "Planning substantially complete, with a known reconciliation pass outstanding" would be the honest framing.
- **[SHOULD-FIX] The status dashboard uses "✓ designed" check-marks that read as "done."** ADMIN §3 marks six domains "Spike N designed ✓ (ready to build)" and Phase-1 domains "designed ✓." The check-mark + "ready to build" reads as completion; the substance is "a detailed paper design exists, zero lines of engine code, zero benchmarks run." The prose footnotes admit this, but the at-a-glance table does not. Consider a distinct glyph for designed-not-built.
- **[NOTE] "100k @ 60 UPS" is honestly caveated** — factory-sim §7.3 splits PASS (forced-active 100k) from PARTIAL (realistic-mode only) from FAIL, names the bandwidth bottleneck, and concedes Mass Entity binding overhead (G8) is an unproven D-001 stress point. This claim is *not* over-sold. Good.
- **[NOTE] Seamless traversal / patched-conics / the render wall** are all correctly tagged as gated on building. No complaint.
- **[MINOR] The render-wall budget in rendering.md §5 RC-8 is a paper estimate dressed with specific numbers** ("~2 M instance ceiling," "single-digit MB/s," "tens of draw calls"). The numbers are plausible and the *mechanism* (O(items)→O(lines) collapse) is sound, but four named residuals (LOD-0 `pathUnitToWorld` build cost, Nanite-on-small-meshes, LOD-band hysteresis, camera-cut bursts) remain unmeasured. The doc does flag them — just make sure no one downstream cites the budget table as a *result*.

## 4. Gaps & omissions (things with NO owner / no plan)

This is the second-most-important section. The domain decomposition is thorough *within engineering*, but several whole categories of shipping a game have **no controller, no decision, and no phase**.

- **[BLOCKER for "build-ready," SHOULD-FIX overall] Build toolchain & CI: no owner, and it is the literal next blocker.** Every "ready to build" statement ends with "...needs a real UE5 project + toolchain" (ADMIN §2/§7, PHASE1-PLAN §11, every spike §8). Yet **nothing in the repo plans that toolchain**: no C++/UE5 project scaffold decision, no CI, no build-farm/automation, no "who stands up the repo." The single thing gating all execution is unowned. At minimum this needs a named owner (core-engine is the natural home) and a M0.5 milestone.
- **[SHOULD-FIX] Automated testing strategy is asserted but never designed.** Every spike says "unit-test X" and "headless harness," which is great intent — but there is **no document defining the test framework, the headless harness's build, CI gating, regression strategy, or how the determinism-hash gates (FS G4, WV1, G2) actually run in automation.** The gates are specified as pass/fail criteria; the *machinery* to run them repeatably is unowned. For a project whose whole de-risking thesis is "prove it headless first," the absence of a testing/CI plan is a notable hole.
- **[SHOULD-FIX] Audio has no owner.** It appears only as a *subscriber stub* to `OnOriginRebased` (spike1-core-engine §1.6, core-engine.md §5) — "audio (world-space sound sources)." There is no audio controller, no decision, no phase, no mention in MASTER_PLAN's roadmap. Spike 1 §7 lists audio as out-of-scope, fine, but it never reappears with a home. For a space/factory game, spatialized audio under floating-origin rebasing is non-trivial and should at least be a named Phase-4 owner.
- **[SHOULD-FIX] Art / asset pipeline has no owner.** "Placeholder art" everywhere; rendering owns *techniques* (scaled space, Nanite, atmosphere) but **no domain owns the asset pipeline, DCC→engine import, LODs authoring, or the eventual art production.** Acceptable to defer, but it should be named as deferred-with-an-owner, not absent.
- **[SHOULD-FIX] No schedule, no team-size, no scope/effort realism anywhere.** This is the biggest *strategic* omission. MASTER_PLAN §7 itself observes that "each pillar has individually consumed years from talented teams" and "none of [KSP/Factorio/DSP/Astroneer/NMS] attempted [all of this] at once." The plan correctly cuts scope in response — but **there is no estimate of how long even the cut v1 takes, with how many people.** Phases are ordered but untimed. For a project explicitly acknowledged as fusing "the two hardest-to-engineer indie games ever shipped," the absence of any effort/time/headcount reckoning is the gap most likely to sink it. A reviewer cannot assess whether "v1" is a 1-year or a 6-year effort — and neither, apparently, can the plan.
- **[SHOULD-FIX] Performance budgets are per-spike, not global.** factory-sim has 60 UPS / 16.67 ms; rendering targets 60 FPS; but there is **no integrated frame budget** (how many ms does the *combined* sim+physics+factory+render loop get, and how is it split?). The render-wall co-validation (Q6) is the one place this collides, and it's owned jointly, but a project-level perf budget (memory ceiling, target hardware spec, the ms split across domains) is not written down. The "commodity desktop CPU/GPU" target is stated but never specified.
- **[NOTE] Networking depth is thin beyond constraints — but honestly so.** The networking controller is "Scoping," correctly treats itself as a day-one *constraint* not a Phase-0 deliverable, and defers implementation to Phase 3. NW-3/NW-4 are still "Proposed." This is defensible (you don't build netcode before the SP slice exists), but two things deserve flagging: **(a) [SHOULD-FIX]** RC-9 (does `FFactoryDelta`/`TickIndex` actually suffice as a replication seam?) is deferred to Phase 3 with *zero* networking-side validation — every other domain confirmed its consumed contracts, but networking has confirmed nothing, so the factory/physics "replication-friendly shape" claims are entirely unaudited by the consumer. **(b)** the "locally-deterministic factory chunk" thesis (NW-4) rests on float-creep not breaking determinism (networking R2), which is acknowledged but unproven and load-bearing for the whole MP factory story.
- **[SHOULD-FIX] MP time-warp is correctly flagged as hard but has no study plan with a date.** Admin Q1 / networking R1 both call it "unsolved-ish" and defer to "a joint mini-study before Phase 3" — but no one owns scheduling that study, and it gates the entire time-warp feature in MP. It's flagged honestly; it just needs an owner+trigger, not just a deferral.
- **[NOTE] Save migration** is consciously and correctly deferred (PS-4: header designed to *enable* migration, machinery deferred to Phase 4). This is the *right* way to defer — design the seam now, build the machinery later. Good. **[MINOR]** one caveat: Phase-1 policy is "schema mismatch → refuse to load," which means *any* schema bump during development invalidates every existing save. For a multi-month build that churns schemas constantly, that's painful in practice even pre-ship; a dev-only "best-effort load" or a save-wipe convention should be noted.
- **[NOTE] Accessibility** is entirely absent. Acceptable at this stage, but for completeness it has no owner and no mention — worth a one-liner that it's a Phase-4+ gameplay/UI concern.

## 5. Process / architecture health

The agentic doc system is **the strongest part of this corpus** — it is coherent, the templates are followed, and the decision logging is mostly disciplined. The defects are drift, not rot.

**Strengths (verified):**

- **[NOTE]** The three-tier model (Admin → Domain → Subagent) and the brief/report formats (AGENT_ARCHITECTURE §4) are real and consistently used — every spike doc reads like the output of a well-briefed agent, with explicit "consumed verbatim / provided / flagged to Admin" sections.
- **[NOTE]** Decision-ID discipline is good: D-/CE-/WG-/PS-/FS-/GP-/RN-/PH- prefixes are used consistently, decisions carry rationale+date+status, and superseded decisions are marked not deleted (PH-4 shows the struck-through original). RC-/C- reconciliation registers are tracked in two places (PHASE0-SUMMARY §4, PHASE1-PLAN §10).
- **[NOTE]** "Link, don't duplicate" is mostly honored — controllers point at spike §-anchors rather than re-pasting. The append-only additive-field discipline (RC-2/RC-7/RC-12) is a genuinely good pattern that kept Phase-1 changes non-breaking.

**Drift / defects:**

- **[BLOCKER] A controller file contradicts the locked cross-domain decision it depends on.** core-engine.md (the *owning* controller for `RegionDepth`) states "Forge 11 / Cinder 9" in its header, CE-9 row, §5 interface, backlog, and R4 — while PHASE1-PLAN §10 has *locked* 9/8. The domain owner's own context file is stale against the Admin-locked value. Per AGENT_ARCHITECTURE §5 ("a stale context file is a bug"), this is exactly the failure the process is supposed to prevent. (Same root cause as §2.1.)
- **[SHOULD-FIX] The Admin "ALL CLOSED" claim is not earned.** ADMIN §2/§6 and PHASE1-PLAN §10/§11 assert C-1…C-9 ALL CLOSED. But C-8 is contradictory across docs (§2.1) and C-1 has stale residue in gameplay (§2.2). The reconciliation *happened* (the right answers exist in PHASE1-PLAN) but the *propagation* didn't — and "closed" was declared on the decision, not the propagation. This is a process gap: there is no step that verifies a locked value reached every consumer doc before "closed" is stamped.
- **[SHOULD-FIX] The "doc-debt to fix at build" escape hatch is being used to carry real contradictions past a "closed/build-ready" gate.** PHASE1-PLAN §10's doc-debt note acknowledges the 11/9→9/8 and 5–6→9/8 staleness but defers fixing it "at build," while simultaneously declaring the surface closed and build-ready. Known contradictions in pinned contracts should block the "closed" label, not ride along as deferred debt — especially when the debt list is itself incomplete (§2.1).
- **[MINOR] Two reconciliation registers (PHASE0-SUMMARY §4 RC-list, PHASE1-PLAN §10 C-list) plus per-controller decision logs** means the same fact (e.g. the chunk extent) is asserted in 4+ places. This is the duplication the process warns against, and it's exactly how the C-8 numbers diverged. Consider a single canonical "pinned constants" table (like D-006 for bodies) for derived cross-domain integers like `RegionDepth`.
- **[NOTE] The subagent logs repeatedly note "the Agent subagent tool was unavailable this session; research run via WebSearch/WebFetch directly."** This is honestly recorded (good), but it means the "spawn subagents" tier of the architecture was largely *not exercised* — the domain controllers did their own research inline. The three-tier model is therefore validated at tiers 0–1 but mostly untested at tier 2. Worth noting that the process as-run was effectively two-tier.
- **[NOTE] Naming:** the project is "Orbital Foundry" in docs but the repo root is "Kerbal Factorio" and CLAUDE.md keeps the "rename freely" placeholder. Harmless, but the body/resource names (Forge/Cinder/Ferrite/Cinderite/Combustite) are well-threaded and consistent — a small sign of care.

## 6. Bottom line

**How solid is this plan, really?** The *design thinking* is excellent and well above the bar for a planning-stage repo. The core architectural bet — generalizing KSP's active/on-rails trick from vessels to the entire factory (D-003) — is the right insight, and it is followed through coherently across every domain. The hardest technical risks are correctly identified, correctly ordered (seamless traversal first, it's the premise), and mostly *honestly* caveated as designed-not-built. The contract surface is, in shape, genuinely well-integrated: the coordinate/frame threading, the ItemId space, the persistence `IPersistable` split, and the active/on-rails proxy contract all hang together. If the goal was "prove on paper that this fusion is architecturally tractable and find the real risks," it succeeded.

**But "build-ready" is not an accurate claim, for three concrete reasons:**

1. **A pinned contract is contradictory across docs (C-8 `RegionDepth`).** The locked value (Forge 9 / Cinder 8) lives in exactly one doc; the owning controller and 3+ other docs still carry 11/9, ≈10, or 5–6 — and the derivation trail contains an arithmetic error. A builder reading the core-engine controller gets the wrong number. **(BLOCKER)**
2. **A "closed" contract has stale dropped state (C-1 `DepositTypeId`).** World-gen removed the indirection; gameplay's docs still implement it. The two domains disagree on a contract both call closed. **(SHOULD-FIX, borderline BLOCKER)**
3. **The thing that gates all execution — the UE5 project + toolchain + CI + test harness — is unowned and unplanned**, alongside whole missing categories (audio, art pipeline, schedule/headcount, global perf budget). **(BLOCKER for "build-ready"; SHOULD-FIX otherwise.)**

**Top 5 things to fix or watch before building:**

1. **Reconcile C-8 `RegionDepth` everywhere and fix the math trail.** Lock Forge 9 / Cinder 8 for the stated 1 km extent, propagate to core-engine (header/CE-9/§5/backlog/R4 + spike §5.5/§8), factory-sim §11.4, persistence §3.1. Then re-state "closed" only once every consumer matches. **(BLOCKER)**
2. **Purge `DepositTypeId` from the gameplay docs** (§2.2, §3.4, §7.2, §8.A struct, §8.C, controller refs) to match WG-11's `Resource = ItemId`. **(SHOULD-FIX)**
3. **Stand up an owner + milestone (M0.5) for the toolchain: UE5 project scaffold, CI, the headless test harness, and the determinism-gate automation.** Nothing else can start without it, and it's currently nobody's job. **(BLOCKER for execution)**
4. **Write down the missing execution concerns even if just as deferrals-with-owners:** a global performance budget + target hardware spec, an audio owner, an art-pipeline owner, and — most importantly — **a rough effort/schedule/headcount reckoning** so "v1" has a size. **(SHOULD-FIX)**
5. **Watch the two carried-over technical unknowns the docs already name honestly:** the integrated render wall (Q6, factory-sim+rendering co-validation) and the Chaos-rebase behavior (R1/G8) — plus get *networking* to actually confirm RC-9, since the factory/physics "replication-friendly" claims are currently unaudited by their consumer. **(NOTE / watch)**

**Net:** This is a strong, unusually disciplined plan with a sound central thesis and honest risk-tagging — but it is **one focused reconciliation pass and a toolchain/execution plan away from being build-ready, and it should stop calling itself build-ready until then.** The weak points are real but fixable, and none of them invalidate the architecture. Fix the C-8 contradiction, scrub the DepositTypeId residue, own the toolchain, and put a size on v1 — then it earns the label.
